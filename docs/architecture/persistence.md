# 数据持久化与恢复

Multidown 将应用状态放在 Tauri 返回的应用数据目录，而下载内容写入用户选择的目录。具体平台位置见[平台路径](../reference/platform-paths.md)，业务代码不应硬编码用户目录。

本页描述的是**代码当前的实际行为**。结论的验证程度逐条标注：本机（Windows）已实际执行、仅有测试覆盖、或尚未在真实环境验证。

## 持久化内容

| 文件 | 内容 | 加载时机 |
| --- | --- | --- |
| `multidown_settings.json` | 用户设置：下载、代理、捕获、BitTorrent 配置 | 启动第一步 |
| `multidown_tasks.json` | HTTP/BT 任务、剩余区间、校验元数据、协议特有状态 | 启动第二步 |
| `queues.json` | 队列定义与任务归属 | 启动第二步 |
| `batches.json` | 批次编排（URL 列表、命名模板、统计） | 启动第二步 |
| `category_rules.json` | 分类匹配规则 | 启动第二步 |
| `schedule_rules.json` | 定时调度规则与总开关 | 启动第二步 |
| `proxies.json` | 命名代理与域名分流规则 | 按需 |
| `torrent-session/` | librqbit fastresume 与会话状态 | 首次需要 BT 时 |
| `native_host_port.txt` | 当前进程的回环端口，退出时尽力删除 | 浏览器集成启动 |
| `first_run` | 首次运行标记（存在则不再自动引导扩展安装） | 启动 |
| `extension/` | 已部署的已解压扩展与导出的 ZIP | 浏览器集成 |
| `multidown.log` | 应用诊断日志 | 随时 |

分类规则的运行时读写都用 `category_rules.json`：启动加载走 `rules_persistence::rules_path`（`RULES_FILENAME`），增删改走 `Scheduler::rules_save_path`，两者一致。仓库源码里出现的字面量 `rules.json` 只是单元测试用的临时文件名，不是应用数据目录里的实际文件名。

批次主要是运行时编排信息，不应假定所有瞬时 UI 状态都会跨重启恢复。

## 版本化存储与迁移

除 librqbit 会话目录外，本仓库自己的 JSON 状态基本都写成带信封的形式（**例外见下**）：

```json
{ "schema_version": 1, "written_at": "<RFC3339>", "data": { } }
```

读取（`storage::load_store`）按以下顺序处理：

1. 三个信封字段齐全时按版本信封解析，其中 `written_at` 不是合法 RFC3339 属于**损坏**：返回 `Corrupt` 并把原文件字节级保留到隔离文件，不会用空状态覆盖。**只有缺少信封字段的裸值**才按版本 0 迁移（这是旧格式的正常路径，不是错误）。
2. 把版本号与数据交给各域的迁移函数，由它补默认值：旧任务没有 `kind` 时恢复为 HTTP，没有种子元数据时保持为空。
3. 迁移函数可以逐条拒绝无效记录。每条被拒绝的记录连同来源路径、域、记录键和原始值写入**隔离文件**，并作为恢复告警返回。**只保留合法记录，不覆盖源文件**。
4. 源文件是版本 0 时，重写为版本 1。隔离文件在重写之前就已落盘并同步，因此重写失败时旧内容仍在（`migration write failed`，源文件与 `.bak` 都保持原样）。

写入（`storage::save_store`）是三步的原子替换：

1. 在同目录写临时文件（`.<文件名>-<uuid>.tmp`，`create_new` 保证不覆盖），写入后 `flush` + `sync_all`；
2. 目标已存在时轮换备份链：`.bak` → `.bak.1` → … → `.bak.N`，新 `.bak` 是替换前的目标副本，并在替换前同步目录（链上旧代不会被自动清理，长期使用需要自行删除）；
3. 用原子替换把临时文件换到目标路径，再同步一次目录。临时文件由 `Drop` 守卫清理，任何失败路径都不会留下半截临时文件。

因此崩溃只会留下**完整的旧文件或完整的新文件**，不会留下被截断的 JSON；被拒绝的旧记录也不会因为迁移而消失。

**平台差异**：原子替换在 Windows 上是 `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`，在 unix 上是 `rename`。父目录同步在 unix 上是真正的 `fsync`，**在 Windows 上是显式的空操作**——Win32 没有可移植的目录 fsync 等价物，所以 Windows 上不声称父目录掉电持久性。

`schema_version < 1` 的写入在创建文件、轮换备份之前就被拒绝，不会污染已有备份。

**例外：`proxies.json` 不走这条路径。** 六个状态文件（`multidown_settings.json`、`multidown_tasks.json`、`queues.json`、`batches.json`、`category_rules.json`、`schedule_rules.json`）都经由 `save_store`（迁移时的重写是同一函数的第 7 个调用点）；代理配置是唯一的例外，它在 `settings/proxy.rs` 里用 `tokio::fs::write` 直接覆盖目标文件——没有信封、没有临时文件、没有 `.bak`、没有原子替换，读取时用 `serde_json::from_str(..).unwrap_or_default()`。后果是：一旦该文件被截断（例如写入过程中进程被杀或断电），下一次读取会**静默退化成空存储**，而下一次保存会把文件改写成只剩新加的那一条，全部命名代理与域名分流规则连同其中的 base64 密码永久丢失，没有隔离文件也没有备份可回退。用户影响见[已知限制](../reference/known-limitations.md#代理配置文件损坏会静默丢失全部配置)。

## 启动顺序

`setup` 阶段按固定顺序执行，顺序本身是契约的一部分：

1. 解析应用数据目录，加载设置（`recover_load` 收集恢复告警）；
2. `Scheduler::initialize` 依次加载任务、队列、批次、分类规则、调度规则，把调度器恢复期告警并入同一列表；
3. 注册自启同步，把恢复告警与调度器交给 Tauri 状态管理（`RecoveryWarnings` / `Scheduler`）；
4. 注册 `multidown://` 深链处理；
5. 扫描启动参数（Windows/Linux 双击文件与冷启动深链）；
6. 启动计划任务 tick（20 秒周期）与**启动恢复**协程；
7. 首次运行时写入 `first_run` 并尝试自动引导扩展安装；
8. 建立托盘图标与 Native Messaging 回环监听。

启动恢复（`recover_tasks`）只处理上次处于活动状态、恢复后处于 `Recovering` 的 HTTP 任务，按创建时间与任务 ID 排序，逐个走**正常队列与并发准入**；用户主动暂停的任务保持暂停。恢复过程中会：

- 校验持久化的区间状态与目标文件长度，不一致时按“整体重下”处理而不是写坏文件；
- 目标不是普通文件（例如被换成了符号链接或目录）时**拒绝写入**并把任务标记为失败；
- 用远端探测校验续传身份（`ETag`/`Last-Modified`/总长度），身份不符时整体重下；
- 汇总失败清单，写入 `[recovery] <task_id>: <message>` 日志。

## 恢复告警与隔离文件

恢复告警的语义是“原始数据已被保留，位置在这里”，不是“数据丢失”。每条告警包含域、消息、记录键和隔离或备份路径。

隔离文件名形如 `<存储名>.recovery-<UTC 时间戳>.json`，与源文件同目录。整份文件损坏（不是单条记录损坏）时，原文件**字节级**保存到同名隔离文件中并返回 `Corrupt` 错误，应用不会用空状态覆盖它。

**“忽略”的语义**：确认告警只清理当前会话的 UI 注册表，**不删除也不修改磁盘上的隔离文件与备份**。因此忽略之后再想找回原始记录，证据仍在。恢复告警列表是当前会话内的一次性提示，重新启动会重新出现。

## 已知可靠性缺口

Windows 上 `save_store` 偶发失败并报 `os error 5`（拒绝访问）或 `os error 32`（文件被占用），约每 6 次“种子在恢复瞬间完成”出现 1 次。持久化互斥锁（`lifecycle_persist_lock`）关闭了一个真实的串行化缺口——所有落盘入口此前并不都在锁内——但**没有**修掉这个报错：并发最强的场景一次都没有复现，进程内并发解释不通，外部文件句柄（例如扫描程序以不带 `FILE_SHARE_DELETE` 的方式持有刚写好的文件）同样合理。

这仍然是**未定位**的缺陷，不是已修复项。诊断时观察 `[persistence-error]` 日志。用户影响与处置见[已知限制](../reference/known-limitations.md#安全与可靠性边界)。

## 敏感数据

任务可持久化认证配置与自定义请求头，设置和代理文件可能包含凭据。它们依赖操作系统用户目录权限，并未声明由应用额外加密。日志和问题报告不得包含 Cookie、Authorization 或代理密码。
