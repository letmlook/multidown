# Multidown v0.3.0 发布硬化设计

## 背景与目标

当前 `main` 已在 `v0.2.0` 标签之后完成磁力链接与种子下载 T1–T6，但现有 GitHub Release 仍是基于旧提交的 `v0.2.0` 草稿。最新代码在本机能够通过前端构建、Rust 测试和 Clippy，但 CI 已暂停自动触发，浏览器扩展安装在 macOS/Linux 上仍可能强制终止浏览器进程，前端缺少自动化测试和 lint，发布文档也存在过期结论。

本轮工作的目标是将当前功能整理为新的正式版本 `v0.3.0`。成功标准如下：

- 扩展安装路径不再强制终止任何用户进程。
- Windows、macOS、Linux 的 push/PR CI 恢复并通过。
- 前端具备可执行的测试和 lint 门禁，Rust 关键状态机测试得到补强。
- 本轮涉及的巨型模块得到有边界的拆分，不进行与发布无关的全面重构。
- npm、Tauri、Rust、Native Host 与文档中的版本信息统一为 `0.3.0`。
- GitHub 标签和 Release 仅在所有验证成功后创建，产物检查完成后正式发布。

## 范围

### 包含

1. 浏览器扩展安装安全修复。
2. CI 自动触发与跨平台门禁恢复。
3. 前端 Vitest、ESLint 基线和首批关键测试。
4. Rust 队列、计划任务、分段、持久化关键边界测试。
5. 浏览器集成逻辑从 `lib.rs` 中定向拆分。
6. `OptionsModal` 中 BitTorrent 设置区域定向拆分。
7. Native Messaging Host 编译警告清理。
8. `v0.3.0` 版本号、CHANGELOG、README 和开发计划同步。
9. 推送、等待 CI、打标签、生成并检查安装产物、正式发布。

### 不包含

- 全面拆分 `lib.rs`、`scheduler.rs`、`OptionsModal.tsx` 或 `index.css`。
- 新增下载协议或新的 BT 功能。
- 为所有既有 UI 补齐完整测试覆盖率。
- 覆盖、删除或复用现有 `v0.2.0` 标签和草稿 Release。

## 设计

### 1. 安全的浏览器扩展安装

后端不得执行 `pkill`、`killall`、`taskkill` 或等价的进程终止操作。浏览器集成模块只负责：

- 准备并定位已构建的扩展目录或安装包。
- 在平台支持时打开浏览器扩展管理页面或启动安装引导。
- 返回明确的结构化结果，说明自动完成的步骤和仍需用户手动完成的步骤。
- 在浏览器不可用、路径不存在或启动失败时返回可操作的错误信息。

前端根据结果展示说明，要求用户自行决定何时关闭或重启浏览器。安装操作不得以用户数据丢失风险换取自动化程度。

浏览器安装与启动实现从 `src-tauri/src/lib.rs` 抽到独立模块，`lib.rs` 保留 Tauri command 编排与注册。

### 2. 测试与 CI

`.github/workflows/test.yml` 同时支持：

- `push` 到 `main`；
- 针对 `main` 的 `pull_request`；
- `workflow_dispatch` 手动触发。

三平台矩阵共同执行 npm 依赖安装、前端构建、前端测试、前端 lint、扩展构建、Native Host 检查、Rust 单测和 Clippy。平台专属代码必须在对应 runner 上编译和检查，不能用单平台结果代替三平台门禁。

前端采用 Vitest 和 ESLint。首批测试优先覆盖可从 UI 中抽离的纯逻辑，例如外部输入/协议分类、任务状态映射和安装引导结果格式化。测试避免依赖真实 Tauri 窗口。

Rust 测试补足以下关键边界：

- 队列并发、暂停/恢复、任务重排和跨天时间窗。
- 计划任务单次触发、去重、启停与限速时间窗。
- 动态分段下限、区间回收和完成状态收敛。
- HTTP 与 Torrent 持久化往返及旧数据兼容。

所有行为变更遵循测试先行；配置和纯文档改动通过静态验证与工作流语法检查确认。

### 3. 有边界的维护性改进

本轮只拆分会被安全修复和测试直接触及的区域：

- 浏览器安装/启动逻辑迁出 `lib.rs`。
- BitTorrent 设置表单迁出 `OptionsModal.tsx`，由父组件传入当前设置、更新回调和操作回调。

拆分不改变现有 Tauri command 名称、前后端数据结构或用户可见行为。其余超大文件作为后续专项重构，不阻塞本次发布。

Native Host 中仅特定平台使用的常量和函数通过 `#[cfg]` 限定，真正无用的实现删除。编译输出不保留已知 `dead_code` 警告。

### 4. 版本与文档

版本统一升级为 `0.3.0`，至少覆盖：

- 根目录 `package.json` 与 lockfile；
- `src-tauri/Cargo.toml` 与 lockfile；
- Tauri 配置；
- Native Messaging Host manifest；
- 安装器和发布工作流中可见的版本信息。

新增或更新 `CHANGELOG.md`，说明 BT 功能、系统集成、安全修复、测试与已知限制。README 中的 Rust 最低版本与 `Cargo.toml` 保持一致。开发计划移除已经完成或已经失效的结论，同时保留仍真实存在的后续债务。

### 5. 发布流程

发布按以下顺序执行：

1. 在隔离工作区完成实现并执行本地全量验证。
2. 合并或推送 `v0.3.0` 发布改动到远端分支。
3. 等待 GitHub 三平台 Test Build 成功。
4. 将最终发布提交合入 `main` 并确认 `main` 门禁成功。
5. 创建并推送带注释的 `v0.3.0` 标签。
6. 等待 Release 工作流生成各平台安装产物。
7. 检查 Release 中的版本、目标提交、资产名称、数量和工作流结论。
8. 将 `v0.3.0` Release 从草稿正式发布。

任何门禁失败时停止发布，保留可诊断状态并修复后重跑。不得覆盖现有 `v0.2.0` 标签或草稿 Release。

## 错误处理与回滚

- 浏览器启动或管理页打开失败时，返回浏览器名称、目标位置和手动操作提示，不执行清场或重试杀进程。
- CI 失败时不创建标签；标签后打包失败时保持 Release 草稿状态。
- 若发布产物不完整，不发布 Release；修复后在相同标签对应提交上重新运行构建，禁止移动已公开标签。
- 若标签已推送但尚未公开且发现代码问题，优先创建修复提交和新版本号，不重写已对外可见历史。

## 验证标准

本地至少执行：

- `npm ci`
- `npm run lint`
- `npm test -- --run`
- `npm run build`
- `npm run build:extension`
- `cargo test --lib`（`src-tauri`）
- `cargo clippy --all-targets -- -D warnings`（`src-tauri`，平台可见范围内）
- `cargo check`（`integration/native-host`，无警告）

发布前还必须确认 GitHub Test Build 三平台全部成功，Release 工作流成功，且 `v0.3.0` 的全部预期资产已经上传。
