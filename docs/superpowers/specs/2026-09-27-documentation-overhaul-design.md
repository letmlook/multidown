# Multidown 文档体系重构设计

## 背景与目标

Multidown v0.3.0 已具备 HTTP 多连接下载、BitTorrent、浏览器扩展、Native Messaging、系统集成与三平台发布能力，但现有文档仍以单篇 README、阶段性实施方案和零散测试说明为主。用户说明、开发说明、架构资料与历史研究互相混杂，部分内容重复，部分命令和平台说明容易随实现变化而漂移。

本次重构建立一个中文为主、面向多类读者、可持续维护的文档体系。完成后：

- 普通用户可以从 README 找到下载入口，并完成安装、首次下载、BitTorrent 与浏览器扩展配置。
- 开发者可以从零搭建环境、运行测试、构建所有组件并理解项目边界。
- 维护者可以按照文档完成版本更新、三平台验证和 GitHub Release 发布。
- 架构文档能解释模块职责、关键数据流、安全边界和持久化策略，但不复制实现代码。
- 历史研究与实施记录得到保留，同时不再干扰当前使用说明。

## 受众与语言

文档服务四类读者：首次了解项目的人、普通用户、贡献者和发布维护者。

主文档使用简体中文。README 顶部提供一句简短英文说明，便于非中文读者理解项目性质；本轮不维护完整英文镜像，避免双语内容长期漂移。

统一命名：

- 仓库与项目名称使用 `Multidown`。
- 安装包、应用窗口和发布标题沿用产品显示名 `MultiDown`。
- 技术名称按官方写法使用，例如 BitTorrent、Native Messaging、Tauri、Chromium、Firefox。

## 信息架构

### 根目录入口

- `README.md`：项目首页，只保留定位、亮点、状态、下载、快速体验、文档入口、参与方式和许可证。
- `CHANGELOG.md`：按版本记录用户可感知变更。
- `CONTRIBUTING.md`：贡献流程、分支与提交要求、质量门禁、PR 检查清单。
- `SECURITY.md`：支持范围、安全边界和私下报告方式。
- `TESTING_GUIDE.md`：改为短迁移页，指向新的开发测试与用户验收文档。

### 现有资料迁移

- `docs/功能模块.md` 的当前模块边界并入 `architecture/`，历史规划部分归档。
- `docs/开发计划.md` 保留为历史路线记录，归入 `archive/`；当前状态由 README、CHANGELOG 和已知限制共同表达。
- `docs/磁力链接与种子下载实施方案.md` 保留为设计记录，归入 `design/`；用户操作和当前架构拆分到相应专题。
- `docs/技术栈选型分析.md`、`docs/IDM核心原理与功能模块分析.md` 归入 `archive/research/`。
- 图标与 Logo 说明继续位于 `docs/design/`。
- `integration/README.md` 改为集成目录的简短入口，链接到浏览器集成架构、用户安装和开发构建说明。
- `docs/superpowers/` 中的设计与计划文件保持原位，作为工程决策记录，不进入普通用户的主要阅读路线。

迁移使用 Git 重命名保留历史。新专题吸收当前有效内容后，旧入口仅保留必要的迁移说明，不复制同一套操作步骤。

## README 设计

README 按以下顺序组织：

1. 项目名称、中文定位和简短英文说明。
2. 当前稳定版本与 GitHub Release 下载入口。
3. 核心能力概览，区分 HTTP、BitTorrent、任务管理、浏览器集成和跨平台能力。
4. 支持平台、运行时要求与已知限制摘要。
5. 面向用户的快速开始：下载安装、添加第一个任务、进一步阅读。
6. 面向开发者的最短启动路径，并链接到完整开发文档。
7. 文档导航、参与贡献、安全报告和许可证。

README 不承担完整安装教程、扩展注册步骤、架构细节、发布流程或长篇功能清单。界面截图只使用仓库内真实素材；若没有合适截图，本轮保留明确的素材待办说明，不生成或伪造产品截图。

## 内容职责

### 用户指南

- 安装文档覆盖 Windows、macOS、Linux 的发布产物选择、系统依赖、首次启动和卸载注意事项。
- 入门文档覆盖 HTTP/HTTPS URL、保存位置、暂停/继续、失败重试和任务状态。
- BitTorrent 文档覆盖磁力链接、`.torrent`、元数据解析、文件选择、做种策略、代理隐私和已知限制。
- 浏览器扩展文档覆盖 Chromium 与 Firefox 的差异、Native Host、固定扩展 ID、安装、验证和常见错误。
- 设置文档按下载、网络代理、BitTorrent、分类规则、计划任务、系统集成组织。
- 故障排查文档按症状索引，并给出检查顺序、预期现象和进一步诊断入口。

### 开发文档

- 环境搭建明确 Node.js 20/22、Rust 1.88+ 和三平台系统依赖。
- 项目结构描述前端、Tauri 后端、下载引擎、BT 引擎、扩展和 Native Host 的职责，不记录易漂移的文件或命令精确数量。
- 测试文档区分前端测试、Rust 单元测试、扩展身份校验、严格 Clippy、手动跨平台验收和网络测试。
- 构建文档说明前置产物依赖、开发构建、正式打包、扩展构建和产物位置。
- 发布文档说明版本同步、CHANGELOG、PR CI、标签、Release 草稿、九类产物检查和公开发布。

### 架构文档

- 总览给出组件图、调用方向与信任边界。
- 下载引擎说明 HTTP 探测、Range、动态分段、写盘、限速、重试和队列状态机。
- BitTorrent 说明输入识别、占位任务、librqbit 会话、文件选择、做种和持久化。
- 浏览器集成说明扩展、Native Host、应用本地端口和深链的完整数据流。
- 持久化说明任务 JSON、设置、BT fastresume 与兼容策略。
- 安全文档说明 TLS、代理隐私、外部输入校验、扩展身份、Native Messaging 来源限制和最小权限。

### 参考资料

- 命令参考以任务为索引，列出仓库真实存在的 npm/Cargo 命令。
- 平台路径集中说明应用数据、日志、Native Host 清单、构建产物与扩展目录。
- 已知限制明确记录 Web Seed、MSE/PE、顺序下载等未支持能力，以及需要公网的验证盲区。

## 事实来源与维护规则

文档事实按以下优先级核对：

1. 当前 `main` 分支代码和配置。
2. 自动化测试与 GitHub Actions 工作流。
3. v0.3.0 公共 Release 及其产物。
4. CHANGELOG 和已经合并的设计记录。

阶段计划、研究笔记和旧 README 不能单独作为“当前已支持”的依据。规划能力必须明确标记为未支持或未来方向。

写作遵循以下规则：

- 操作步骤包含前置条件、命令、预期结果和失败后的排查链接。
- 平台相关说明使用明确的平台标签；浏览器说明区分 Chromium 与 Firefox。
- 同一事实只在一个专题中完整定义，其他文档使用链接引用。
- 不复制大段源码，不使用容易漂移的精确实现数量。
- 公开已知限制和安全约束，不用模糊营销文案掩盖缺口。
- 外部链接优先使用官方文档；项目内链接一律使用相对路径。

## 验证与验收

实现阶段需要完成以下检查：

- 扫描所有 Markdown 相对链接，确认目标文件与锚点存在。
- 扫描 README 和专题文档中的版本号、扩展 ID、命令名与产物名，确保与配置一致。
- 对文档内列出的 npm 脚本执行存在性检查。
- 运行 `npm run test:run`、`npm run lint`、`npm run test:extension` 和 `npm run build`。
- 运行应用与 Native Host 的 Rust 单元测试及严格 Clippy。
- 人工按四条阅读路线复核：首次安装、首次下载、开发启动、正式发布。
- 确认 README 中无失效链接、无把未实现能力描述为已支持、无伪造截图。

验收完成的定义：新用户、开发者和维护者都能仅依赖文档完成各自的核心任务；文档导航无孤立页面；关键事实与 v0.3.0 代码及发布产物一致。

## 不包含范围

- 不引入 VitePress、Docusaurus 等文档站生成器。
- 不创建或部署独立文档网站。
- 不维护完整英文文档镜像。
- 不修改下载功能、界面行为或发布产物。
- 不为截图而生成模拟产品界面。
- 不在本轮升级项目依赖或修复开发依赖审计项。
