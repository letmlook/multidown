## 五、关键技术设计（已落地部分）

### 5.1 动态分段

```
未完成区间: Mutex<Vec<(start, end)>>
worker loop:
  1. take_next_segment(): 取最大段；若 seg.len > 2*MIN_CHUNK → 对半切，本 worker 拿前半，后半放回
  2. 下载该段并写入 offset
  3. 段完成 → 回到 1；全部完成 → 任务完成
暂停: worker 记录当前段已完成区间放回集合
```

### 5.2 令牌桶限速

```
struct TokenBucket { rate_bps: AtomicU64, tokens: Mutex<f64>, last: Mutex<Instant> }
async fn acquire(&self, want: usize) -> usize   // 返回实际可读字节数
```
- 读流循环：`bucket.acquire(chunk.len()).await` 后限速生效（`scheduler.rs:1358`）
- 零限速值 = 不限速（桶直通）
- 计划任务 `SpeedLimit` 事件直接改 `rate_bps`；恢复时回写设置里的静态值

### 5.3 定时调度

- `setup` 中 `tokio::spawn` tick 循环（20s），分发 `ScheduleEvent::{StartTask, PauseAll, ResumeAll, SpeedLimitActivated, SpeedLimitDeactivated}`
- 同一规则同一分钟只触发一次；`Once` 触发后自动禁用
- 与手动暂停互斥：`ScheduledPause` 不覆盖用户手动暂停

### 5.4 规则 / 代理的统一应用点

- 任务创建入口（手动 command + 扩展 TCP 消息 + 批量编排）收敛到 `create_task_internal`
- 分类规则改写目录、查重在这一处完成
- 代理分流在 worker 启动时按 URL host 匹配（`scheduler.rs:398-405`）

## 六、风险与约束

| 风险 | 缓解 |
|------|------|
| 核心下载路径改动回归风险高 | 已补 `task.rs` / `queue.rs` / `schedule.rs` / `persistence.rs` 回归测试；继续扩大场景覆盖 |
| 限速在分段并发下难以精确 | 桶放在全局层而非每连接层；每任务级限速需串联而非并联 |
| Node 24 下前端构建失败 | 锁定 Node 20/22；计划用 `.nvmrc` + `engines` 提前拦截 |
| Windows / Linux 行为本机无法验证 | 依赖 CI 三平台构建 + 发布前远程验证 |
| MV3 service worker 休眠影响 native messaging | 现有实现为按需唤醒模式，保持现状 |
| lockfile 依赖镜像源导致 CI 失败 | `resolved` 已全部指向官方源并新增 `.npmrc`；如需加速请用命令行 `--registry` 临时覆盖 |
